## 4. VPNResellers API v4.1 — verified contract

Source: <https://api.vpnresellers.com/docs/v4_1/> (read 2026-10-27).

- **Base URL:** `https://api.vpnresellers.com/v4_1`
- **Auth:** `Authorization: Bearer {token}` for account management. `/un/accounts/*` uses the
  end user's Basic auth (not used server-side here). `/geoip` needs no auth.
- **Content type:** JSON in/out. `Accept: application/json`.
- **Account statuses:** `Active`, `Disabled`.
- **`expire_at`:** `YYYY-MM-DD` or `null` (null clears expiry → provider auto-renewal).
- **Errors:** `400, 401, 402 (insufficient balance), 403, 404, 405, 422`; `validate` also
  returns `460` (username not found) and `461` (bad password).

| Operation | Method & path (per docs) |
|---|---|
| Check username | `GET /accounts/check_username?username=` |
| List accounts | `GET /accounts?page=&per_page=&status=` |
| Create account | `POST /accounts` `{username, password, customer?}` |
| Retrieve account | `GET /accounts/{id}` |
| Delete account | `DELETE /accounts/{id}` |
| Enable / disable | `PUT /accounts/{id}/enable` · `PUT /accounts/{id}/disable` |
| Change password | `PUT /accounts/{id}/change_password` |
| Set expiry | `PUT /accounts/{id}/expire` `{expire_at}` |
| Validate credentials | `POST /accounts/validate` |

### Documented API inconsistencies (do NOT guess)
1. The by-id **disable** heading reads `PUT v4_1/{account}/disable` while its example posts
   to `/un/accounts/enable`. The client uses `/accounts/{id}/disable`; confirm with support.
2. **Rate limits** are not documented anywhere in the public docs.
3. **Suspension billing behaviour** ("disabled accounts stop daily charges") is not in the
   API docs. It was communicated informally; treat as unverified.
4. **Protocol/device limits** (10 devices, WireGuard single key, VLESS via API only) are not
   in the API docs and must be confirmed in writing before publishing claims.
5. Creating a `customer` requires a `project_id`; the value for our account is unknown.

These are recorded as blockers, not implemented assumptions.

## 6. Payments & order lifecycle

Implemented as a sandbox foundation (Phase 2) plus a flag-gated sandbox Checkout (Phase 3),
see §14–§15. Nothing is live: live keys are refused in code and the sales flags default to off.

- **Paid** is accepted only from a signature-verified webhook with matching amount and
  currency, through `markVpnPaid()` (single atomic UPDATE).
- **Provisioning** runs only through `provisionVpnOrder()` after an atomic claim.
- **Refunds** are recorded even if they arrive before the paid event; the order becomes
  `cancelled` and a later paid event is ignored. Refunds do **not** suspend the provider
  account (business rule unverified).
- **Ambiguous provider creates** (timeout/network) become `reconciliation_required`; the
  account is found by its deterministic username and never created twice.
- **Recovery:** a definite failure releases the claim; an admin can run `reconcile`
  (lookup only) and then `provision` (retry) with CSRF.

**Status:** implemented locally behind a flag; LIVE payments remain BLOCKED.

## 8. White-label app distribution (Phase 5)

**BLOCKED.** No provider application binaries exist in the repository (`public/` contains only
site icons/OG images). Nothing was downloaded, copied, renamed, or uploaded.

### Immutable-binary procedure (to apply once files are supplied)
1. Obtain the original file directly from VPNResellers or the account's official download page.
2. Record: original filename, platform, version, byte size, source, SHA-256.
3. Copy → rename only the download filename (allowed characters, real extension only).
4. Recompute SHA-256; it **must** equal the source. Compare byte size too.
5. On any mismatch: delete the copy and investigate; never patch the binary.

Prohibited: decompiling, unpacking/re-zipping an APK, patching, editing metadata/resources,
re-signing, repackaging, changing internal branding.

### Permission questions to send VPNResellers before hosting anything publicly
1. May TOPVPN host the supplied binaries on its own infrastructure?
2. May they be distributed directly to end users (not via a vendor page)?
3. May the downloadable filename be changed (contents unchanged)?
4. Which platforms/versions are covered, and is this permitted under our plan?
5. Are official app-store links available for each platform (preferred over binaries)?

Until answered in writing: no public binary hosting.

## 9. Security notes

- Provider token is read only by `loadVpnResellersConfig()` and placed only in request
  headers. Provider error text is sanitised and truncated before it is returned, so an echo
  of the token or the submitted VPN password cannot leak into logs or the admin UI.
- Mutations are never auto-retried (duplicate create would double-charge balance); safe GETs
  retry once with a timeout that also covers the response body.
- `VPNRESELLERS_API_URL` must be `https:` (enforced) so the bearer token is never sent in clear.
- Payloads expose `wg_private_key`; the portal must never send provider records to the
  browser except the authenticated owner's own values.
- No secret was printed or committed; `.dev.vars` remains gitignored.

## 14. Phase 2 — VPN sales foundation (sandbox, local only)

Status: implemented locally; **not deployed, not migrated remotely, no live calls**.

### Schema (new migration, not applied)
`migrations/0003_vpn_orders.sql` creates, with no relationship to `ads_orders`:
`vpn_orders` (four independent status columns), `vpn_payment_events` (PK = Stripe event id),
`vpn_provisioning_claims` (PK = claim key, `order_id UNIQUE`), `vpn_accounts`
(`provider_account_id`/`username` UNIQUE) and `vpn_order_events` (append-only audit).
Money is stored in integer cents with an explicit currency; `provider_account_id` has a
partial unique index on `vpn_orders`.

### Lifecycle
`worker/vpn/state.ts`: `pending_payment → paid → provisioning → active → expired`, plus
`provisioning_failed`, `reconciliation_required`, `cancelled`, `refunded` (terminal).
Transitions are asserted in the repository (not just documented). Refunds do not suspend
the provider account.

### Routes
| Route | Auth | Purpose |
|---|---|---|
| `GET /api/vpn/plans` | public | catalog + `checkout: closed/sandbox` |
| `POST /api/vpn/orders` | flag-gated | pending order, server-priced |
| `POST /api/vpn/webhook` | Stripe signature | paid/refund events |
| `GET /admin/api/vpn/orders/:id` | admin cookie | status + provisioning state |
| `POST /admin/api/vpn/orders/:id/reconcile` | admin + CSRF | lookup, never creates |
| `POST /admin/api/vpn/orders/:id/provision` | admin + CSRF | retry after confirmed-missing |

No customer-facing order read exists (identity blocked). No checkout redirect exists.

### Guarantees enforced in code/tests
- Browser price/duration fields are rejected (422).
- `markVpnPaid` is one atomic UPDATE; duplicate events are a no-op.
- Claim row is inserted before any provider call; concurrent claims yield exactly one winner.
- A create timeout/network maps to `reconciliation_required`; no second create.
- A definite failure releases the claim for a later authorised retry.
- A refund recorded before payment cancels the order and blocks the delayed paid event.
- Domain isolation: non-`vpn` events never touch a VPN order; the ads webhook/secret/table
  are unchanged and separate.
- Provider token, webhook secret and the HMAC-derived account password are never persisted
  in orders or returned by any route.

### Deliberately not built / limitations
- **Intro ($3) price is disabled** until verified identity can enforce "one per customer".
  The catalog shows `introCents` but orders are always regular price.
- **Sandbox Checkout** exists in Phase 3 behind two flags and an `sk_test_`-only guard;
  no real Stripe run was executed (no test key configured).
- **No customer portal / authenticated order read** (identity blocked).
- Rate limiting reuses the generic `ads_rate_limits` table with a `vpn-order:` key.
- Cross-isolate concurrency is proven only at the D1 unique-key level; the in-isolate
  `Promise.all` test does not simulate two PoPs.
- Partial refunds are recorded for manual review, not auto-handled.
- Refund events without `vpn_order_id` rely on `payment_intent` propagation (unverified).

46 VPN-domain tests cover state transitions, D1 idempotency/concurrency, provisioning
success/timeout/failure/retry, reconciliation, webhook replay/order/refund/mismatch,

## Manual Renewal Only (Product Requirement) � Phase 10

### Billing policy
- All purchases are one-time payments for a fixed access period.
- No Stripe Subscription objects or recurring Prices are created (mode=payment).
- No auto-renew, off-session, or saved-card charges.
- Every renewal is a new one-time Stripe Checkout Session with server-controlled price/currency.

### Renewal eligibility (server-side, UTC)
- Order must be active + paid + provisioning_status=succeeded.
- Entitlement expiry must be within RENEWAL_WINDOW_DAYS (30 days).
- Exact 30-day boundary is eligible; 30 days + 1 second is not.
- Expired entitlements cannot be renewed (customer repurchases).
- Unpaid/foreign-owned orders rejected.

### Renewal flow
1. Customer clicks Renew on /account/orders/:id (only shown when eligible).
2. POST /api/vpn/orders/:id/renew (customer-authenticated, CSRF-verified, ownership-checked) creates a Stripe Checkout Session with metadata.renewal=1.
3. Customer pays on Stripe; redirected to /checkout/success?order=...
4. Webhook checkout.session.completed with metadata.renewal=1:
   - Verifies amount/currency match the order.
   - Calls extendVpnExpiry which extends expire_at by interval_months from the current expiry (never from now).
   - Records renewal_extended event.
   - Idempotent: duplicate event id returns 200 without re-extending.
5. Abandoned checkout leaves current access unchanged (no webhook means no change).
